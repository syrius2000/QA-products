# Design

## Context

通常QAは `quality-loop/qa_workflow/workflow.py` の `Workflow` が状態を管理し、`cli.py` が操作を公開している。`plan`、`approve`、`submit`、`publish`、`requa` は既に個別操作として存在し、各操作は `revision` で整合を取り、`store` が状態を原子的に保存する。承認は `approve` が利用者の発言と計画ハッシュ（`fingerprint`）を受け取って記録する。

既存の操作の意味は変えず、それらを順に呼ぶ層を追加する。See proposal.md - Why / What Changes.

## Goals / Non-Goals

**Goals**
- 承認後の修正・提出・公開・再QA依頼を、1操作で順に進める。
- 途中失敗から、完了済みの段階を重複させずに再開できる。
- 「軽微な変更」の判定を、人の解釈に依存せず機械的に行う。

**Non-Goals**
- `blind-qa-cycle` の変更。
- 再QAの判定（レビュー）の自動化。判定は別担当に残す。
- 起動の自動化（スケジュールやトリガー）。起動は人が行う。

## Decisions

### D1: loopは `Workflow` の新メソッドとして実装し、CLIに `loop` を追加する
- 理由: 状態の保存、`revision` の照合、イベント記録を既存の仕組みで一箇所にまとめられる。段階ごとの再開もこの状態に対して行える。
- 代替案: Skill側のスクリプトで既存CLIを順に呼ぶ。却下理由: 段階の完了状態を別管理することになり、途中失敗時の整合を保証しにくい。

### D2: 各段階を状態に記録し、段階単位で再開する
- 段階は `commit`、`submit`、`requa-request`、`finalize`、`publish` の順に5つとし、完了時にイベントとして記録する。`requa` は次の再QA依頼を作り、`finalize` でその依頼を確定してから、`publish` で公開する。公開の指示が無い場合は、再QA依頼を作る前（`requa-request` の前）で停止する。
- 再実行時は、記録済みの段階を飛ばし、最初の未完了段階から再開する。
- 理由: 「push後に失敗した」場合に、commitやpushを二重に行わないため。

### D3: 軽微な変更の判定は純粋関数として実装する
- 入力は承認済み計画（対象パス、完了条件、受入基準、確認方法）と、実際の変更（パス、行数）。出力は「軽微」か「停止」と理由。
- 判定規則は、変更パスの部分集合、新規パスなし、完了条件・受入基準・確認方法の本文ハッシュ一致、行数上限以下の4つ。
- 理由: 純粋関数にすると、規則をテストで固定でき、判定の根拠を記録として残せる。
- 代替案: 利用者やAIの判断に委ねる。却下理由: 「軽微」の解釈が担当ごとにずれる。

### D4: 行数上限は `qa_workflow` 内の定数とし、リプレイ検証で決める
- 上限値は `qa_workflow` 内の名前付き定数として定義する。初期値は未定とし、リプレイ検証（tasks 9.2）の結果で決める。
- 理由: 値の変更がコードの変更として履歴に残り、判定規則の変化を追えるようにするため。
- 代替案: 外部の設定ファイル。却下理由: 値を変えやすい反面、判定規則の変化が設定の変更として見えにくくなる。

### D5: commitは承認文の範囲に限り、`gitops` で承認済みパスだけをステージする
- 承認文に「修正後のcommitまで」が含まれる場合だけ、承認済みパスをステージしてcommitする。`git add -A` は使わない。
- 理由: 既存の固定制約（commitは明示依頼のみ）と、ステージの範囲外を含めない既存規則を守るため。

### D6: 公開前検査と祖先確認は既存の仕組みを再利用する
- 機密情報と個人パスの検査は、既存の `publish` が行う検査を呼び出す。新たな検査を作らない。
- 再QA依頼前の祖先確認は、`gitops.ancestor` を使う。

### D7: 同一指摘の反復は、Finding IDの履歴から判定する
- 前サイクルと今サイクルの未解決Finding IDを比較し、連続2サイクルで一致したら停止する。
- 3サイクル上限は、サイクル数を状態から数えて判定する。

### D8: 承認文は利用者の発言そのものとしてのみ受理する
- `approve` の `message` 引数を、loop がAIの生成文として作らない。loop は利用者から受け取った発言だけを渡す。
- 既存の `approve` の計画ハッシュ照合を、そのまま使う。

## Risks / Trade-offs

- [段階の追加で状態の形式が変わる] → 既存の状態を読める後方互換を保ち、新しい段階フィールドは未設定を既定値とする。
- [軽微判定の規則が厳しすぎると、再承認が頻発する] → リプレイ検証の結果で行数上限を調整し、判定理由を記録して検証可能にする。
- [段階の再開で、外部状態（remote）と記録がずれる] → 再開時に `origin/<branch>` の状態を確認してから続行する。ずれがあれば停止して `status` で示す。
- [loopが修正と判定の両方を担う誤用] → D1で判定を含めず、再QAは別担当への依頼として返す。

## Migration Plan

1. 既存の操作（`plan`、`approve`、`submit`、`requa`）はそのまま残し、loopを追加する。既存の利用手順は変えない。
2. テストを先に書く（判定規則、段階の再開、承認文の検査、同一指摘の停止）。
3. 過去の `unify-blind-qa-cycle` の指摘でリプレイ検証を行い、行数上限を決める。
4. ロールバック: loop操作をCLIから外せば、既存の手動手順だけが残る。既存操作は変更しないため、戻し作業は loop 関連の追加分に限る。

## Open Questions

- 行数上限の初期値（D4）。リプレイ検証の結果で決め、仕様の構造は変わらない。
