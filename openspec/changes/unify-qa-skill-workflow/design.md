## 背景と設計の境界

動機と機能範囲は[提案](proposal.md)、外部から観測できる契約は[仕様](specs/unified-qa-workflow/spec.md)、現在の承認境界は[計画031](../../../docs/Artifacts/implementation_plan_031_1004.md)に記載する。

旧Quality Loopは案件正本・Role・handoff・実装許可を持つが、通常のクラウドQAではこれらの手動準備が操作負担となっている。クラウドAIにはGitHub閲覧・Markdown作成を依頼できる一方、Pythonや旧CLIの利用可否は保証されていない。既存blindは固定SHAと独立性を持つが、結果回収と初回要件の継承が十分に定義されていない。

この設計では通常QAを独立した軽量運用にし、旧caseエンジンを呼び出さない。旧2スキルの正式案件運用は保持し、明示的にその運用を選ぶ場合だけ旧入口へ案内する。旧caseへの自動昇格、結果からの自動case更新、配布先の追加機能の一括逆同期は行わない。

## 達成することと対象外

達成することは、平易な会話操作をローカルの検査可能な状態へ結び付け、クラウドには自己完結した依頼と一つのレビュー契約だけを渡すことである。AIが行う意味の判断と、CLIが行う対象・構造・状態の確認を分ける。

クラウドAIの起動・送信、製品コードのクラウド修正、旧case契約改訂、既定ブランチの改名、自動merge、外部スキル配置は対象外である。クラウドの製品機能や書込み能力は仮定せず、返却形態ごとに取得できた事実を記録する。

## 構成の判断

### 1. 新しいローカルruntimeを自己完結したスキルへ同梱する

開発正本を`quality-loop/qa_workflow/`、配布パッケージを`quality-loop/skills/quality-qa/`とする。パッケージには`SKILL.md`、`VERSION`、`CHANGELOG.md`、`bin/quality-qa-cli`、`runtime/qa_workflow/`、操作別参照、Markdownテンプレート、代表会話の検査入力を含める。

ローカルCLIはPython 3.10以上の標準ライブラリを使い、Gitと設定済み`gh`を子プロセスとして利用する。Skill配置位置からruntimeを解決し、呼出し元の作業ディレクトリを保つ。クラウドにはこのパッケージを要求しない。

旧エンジンへすべてを追加する案は、クラウドQAにも正式case準備を持ち込み、旧互換の検証範囲を広げるため採らない。自然言語の長い指示だけで運用する案は、SHA・履歴・結果の対応が曖昧になるため採らない。

### 2. 利用者の会話操作とローカル検査を分ける

| 利用者の操作 | ローカルの責務 | 自動で行わないこと |
| --- | --- | --- |
| QA依頼文を作って | 環境取得、目的・基準の整理、対象確定待ちの下書きまたはSHA固定済み依頼の生成 | commit、push、AIへの送信 |
| クラウドQAに出して | 公開集合表示、承認範囲照合、対象commit、依頼commit、topic push、可視性確認 | 既定ブランチへの公開、範囲外履歴の公開 |
| ローカルQAに出して | 対象確定後に別担当へ渡す依頼生成。未commitなら下書きと対象確定の案内 | 暗黙commit、push、自己QA |
| この対象をローカルでcommitして | 表示済み対象と内容の承認照合、対象限定commit、正式依頼の確定 | push、対象外変更のcommit |
| QA結果を確認して | 結果取得、構造検査、AIによる内容確認、修正計画保存 | 製品修正、独立検証の代行 |
| この計画で修正して | 対象計画の承認記録、許可範囲の修正・確認・提出記録 | 自己解消判定、再QAなしの終了 |
| 再QAに出して | 前回指摘と元基準の継承、新対象固定、宛先に合う依頼生成 | 宛先未指定でのクラウド公開 |
| QA状況を教えて | 最新の有効な状態読取、次操作の導出 | 状態更新、採番、ファイル生成 |

AIは目的理解、重要な不足事項の質問、指摘の妥当性評価、修正計画本文、承認範囲の製品修正を担当する。CLIは識別・構造・保存先・承認記録・対象集合・状態遷移を検査する。CLIの成功を意味の妥当性やテスト成功と同一視しない。

CLI入力はSkillが組み立て、通常の利用者には日本語の説明と依頼文を表示する。内部コマンドは準備、対象確定、公開、取込、訂正依頼、計画登録、承認登録、修正提出、再QA、状態確認を分離する。公開には実際のユーザー発言と表示済みの対象集合を対応付け、自由な指示本文をシェルコードとして評価しない。

### Phase 0. Git preflightと実装baseline

QA依頼前にGit監査を求められたら、CLIのread-only `preflight`でrepo root、branch、完全HEAD、upstream/default branch、staged・unstaged・untrackedのファイル別状態とdiff statを返す。状況確認ではstate、index、ファイルを書き換えない。Skillは適用AGENTS・QA規則・目的・受入基準・必須検証を確認し、変更pathを今回の対象、無関係な既存変更、未分類に分ける。clean checkoutならbaseline SHAとclean statusを記録する。dirty checkoutは自動修復せず、対象の分離方法を示して人の選択を待つ。別worktreeが必要なら既存内容を保持し、baselineと初期差分を照合する。

既存WIPからcheckpoint commitを作るのは、利用者が`blind-qa-cycle checkpoint`を明示した場合だけとする。非default topic branch、承認pathのみのindex、unstaged/untrackedなし、完全な開始点が確認できることを事前条件とし、1条件でも満たさなければ停止する。新規実装でclean baselineを作るときは、既存変更をユーザーの明示操作で別保存・commitするか、隔離したclean worktreeを開始点から用いる。暗黙のstage/stash/reset/clean/restoreはしない。

### 3. 下書きと正式依頼を分け、対象版と差分を固定する

初回は開発開始点を`initial_baseline`と`baseline`に、今回対象を`reviewed`に固定する。既存開発ブランチを使う場合は開始点を履歴から確認し、特定できないときだけ質問する。QA対象を推測するcheckpoint commitは要求しない。受入基準は元の文章を順序付きで`AC-001`から採番し、依頼、レビューMarkdown、機械記録で全件・原文・順序・fingerprintを照合する。欠落・追加・重複・改変・並べ替えがあれば結果を有効化しない。

依頼の準備時に、対象に含める追跡ファイルの変更・削除と未追跡ファイルを確認する。今回レビューしたい内容が既存commitに含まれない場合は、`対象確定待ち`の下書きとして目的・基準・対象パス・内容識別を保存する。`reviewed`は未確定とし、旧HEADを代入しない。下書きは正式依頼として手渡せず、レビュー取込の対象にもできない。意図的に既存commitだけをレビューする指示がある場合は、そのSHAを固定し、ローカルの追加変更が対象外であることを表示する。

ローカルQAは表示済み対象への明示的なローカルcommit指示を別途受けるか、ユーザーが作成したcommitを確認して対象を確定する。ローカルcommitには公開と同じ対象・index・既存差分保持の検査を適用するが、pushはしない。クラウド公開の明示指示は、表示済み範囲の製品commitと依頼commitを含む。対象をcommitする直前に下書きの内容識別と承認済み集合を照合し、変更があれば再表示・再承認へ戻る。commit後に内容一致を確認してSHAを固定し、同じ下書きの依頼ID・予約サイクルを正式依頼へ確定する。確定済み依頼は後から別SHAへ書き換えず、変更された対象には新しい依頼を作る。修正提出の内容識別だけではこの確定を省略できない。

再QAの`baseline`は前回の`reviewed`とし、`initial_baseline`、初回目的・受入基準の本文と識別値、未解決指摘一覧を維持する。差分確認は`baseline..reviewed`、元要求との確認は`initial_baseline..reviewed`および固定要件を参照し、いずれも次の対象集合の選別を適用する。目的・基準の変更は既存履歴の書換えにせず、ユーザーに確認して新しい版として記録する。

クラウドへ渡すパスはリポジトリ相対とし、依頼中の要件と対象の指紋を一致検査に使う。指紋は取り違え検知のためで、レビューの品質や独立性を証明するものではない。

製品対象集合`P`と、当該QA履歴で生成・取得した運用成果物の正確な相対パス集合`O`を記録する。`O`には依頼、レビュー原文、訂正依頼、修正計画、状態などの各生成記録を関連付ける。未登録ファイルを名前やDIRだけで運用成果物と推測しない。製品としてレビューする要件書・計画書は`P`に含め、`P`と`O`が重なる場合は分類確認待ちにする。各差分の全変更パス`D`から製品差分`D ∩ P`、運用差分`D ∩ O`、範囲確認が必要な残りを区別して表示する。残りは黙って除外せず、対象への追加または対象外とする理由を確認・記録してから正式依頼を確定する。改名では旧・新パスの両方を確認する。

依頼には`P`・`O`と範囲判断を含め、クラウドも同じ選別を再現できるようにする。製品版A→依頼I→レビューR→修正版Bでは、AからBの製品差分からI・Rの登録パスを除き、レビュー自体は根拠として参照する。`docs/Artifacts/`全体を除外しない。この選別はレビューの見せ方であり、pushされる履歴の承認範囲検査を緩めない。

### 4. クラウドのレビュー契約をMarkdownだけで固定する

新しいレビュー契約を`unified-qa-review-v1`とする。依頼には全文の記載例を埋め込む。レビューは次の構造を持つ。

1. 日本語タイトルとcreated/update/author。
2. 契約名、依頼ID、リポジトリ、開発ブランチ、初回基準SHA、差分基準SHA、対象SHA、サイクル、要件指紋、担当識別、提出版番号、訂正ID、置換対象の原文SHA-256の固定項目。初回の提出版番号は1、訂正IDと置換対象は「なし」とする。
3. 結論。内部Gateは`PASS / HOLD / FAIL / INCONCLUSIVE`とし、通常表示では日本語の説明を添える。
4. 確認した範囲、check IDごとの実行結果、未検証事項。check結果には状態、実際のargv・cwd・環境version、開始／終了時刻または所要時間、exit code、stdout/stderr（または保存済みlog pathとhash）を持たせる。確認範囲の記載は指摘0件でも必須。
5. 指摘ごとのブロック。ID、種別、重大度、要求との対応、対象版での根拠、影響、修正または確認案、完了条件、検証方法を持つ。
6. 前回指摘の再確認。各IDに確認結果と根拠を対応付ける。初回は対象なしと明記する。
7. 残余事項と保存先・返却参照。

固定項目と指摘IDは決まった見出し・箇条書きで読めるようにし、解説本文は自由な日本語とする。ローカル解析は限定した文法を使い、一般Markdown全体を理解しようとしない。引用やコードブロック内の見出しを状態項目と誤認せず、欠落・重複・不正な列挙値を拒否する。

結論だけを読んで状態を進めない。`PASS`と重大未解決指摘の併存、必須checkの未実施・error、前回指摘への確認不足は訂正・追加確認へ進める。必須checkの非zero exitは`FAIL`、実行不能は`INCONCLUSIVE`、SHA・Skill・check契約の不一致は`HOLD`とし、状態要約はcheckごとのEvidenceから導出する。`required_checks`は互換用の総括に留め、個別Evidenceの代用にしない。環境不足自体を再現済み不具合へ置き換えない。修正案も元要求と根拠に照らしてローカルAIが吟味する。

実行契約はstable check ID、kind、required、argv配列、cwd、明示された環境変数、timeout、期待exit code／結果を持つ。commandはshell文字列として評価せずargvとして実行する。必要なPython／tool versionを前提に記し、依存install、network、credential利用は個別許可なしに行わない。依頼に固定された必須checkがすべてPASSでなければ総合PASSを許さない。任意checkのNOT_RUNも未検証事項に残す。

JSONもクラウドへ書かせる案は操作負担と環境依存を増やすため採らない。無定形の自由文だけの案は取り違え検査と再QAでの追跡を難しくするため採らない。

### 5. GitHubのレビュー取得にコード全体のmergeを使わない

取得入口は現在の依頼記録、GitHubブランチ参照、PR URL、本文ファイルである。通常は現在の依頼に記録されたリポジトリ・ブランチ・レビュー相対パスを使い、利用者に毎回入力を要求しない。

GitHubでは`gh`を主に利用し、選んだブランチまたはPRのコミットを完全なSHAへ解決して、その版の指定Markdownを取得する。取得元リポジトリ、PR番号・ブランチ、コミット、元パス、取得時点、原文SHA-256をローカルへ記録する。別ブランチ・PRでもレビュー本文の依頼IDと対象版を元依頼へ照合する。

PR全体をmergeしたり、ユーザーのチェックアウトをpullしたりして回収しない。レビュー原文の保存先が同名で存在する場合は同一内容なら再利用、異なる内容なら停止する。訂正は次の追記式手順で新しい取込版として記録し、過去結果を置き換えない。

1. 不備結果も原文と取得元・SHA-256を保持する。訂正依頼操作で訂正ID、次の提出版番号、置換対象の原文SHA-256、新しい採番済みレビュー保存先を予約し、`qa_correction_NNN_MMDD.md`へ保存する。依頼ID・サイクル・対象SHA・初回／差分基準・要件指紋は元依頼から継承する。元依頼は変更せず、訂正依頼を追加の許可保存先の根拠にする。同じ訂正依頼の再試行は既存予約を再利用する。
2. クラウドへ訂正依頼を手渡しし、新しい保存先へ全項目を含む訂正版を要求する。訂正依頼のGitHub公開には明示的な公開指示が必要で、本文の手渡しも可能とする。元パスの内容が変更されて返った場合は受理せず、予約した新パスへの提出を案内する。本文返却も同じ訂正ID・提出版・予約保存先の契約で取り込む。
3. 取込時は元依頼に加え、未処理の訂正ID、提出版番号、置換対象ハッシュ、予約パスを照合する。対象SHAや要件が変わったものは訂正として受理せず、新しいQA依頼へ案内する。各原文は別パスで保持する。
4. 構造検査とAIによる内容確認の両方が完了した訂正版だけを有効版として選び、前版との置換関係を記録する。未検証事項は別に残す。不備訂正版では有効版を切り替えず、さらに次の訂正を案内する。訂正待ちの間は以前の有効版があっても、それを使って修正許可・解消・終了判断を進めない。置換対象が最新の訂正対象でない古い提出は有効版へ戻さない。
5. 同一依頼・訂正ID・提出版・原文ハッシュの再取込は既存結果を再利用する。取得元が追加された場合は出典だけを追記する。同じ提出版の別内容や未予約パスは拒否する。訂正だけで製品版・QAサイクルを進めず、前版の指摘を記載省略だけで解消しない。

本文返却は取得元コミットを確認できないことを記録する。取得不能・認証失敗は結果待ちのまま必要条件を返し、未取得のファイルを推測して生成しない。リポジトリ外へ出る相対パス、許可外の出力先、外部を指すシンボリックリンクを結果取込先にしない。

### 6. 修正計画と技術判定の責任を分ける

結果確認はまず原文と依頼の整合を検査し、その後AIが指摘を要求未達・目的に直結する不具合・改善提案・未検証へ整理する。意味の評価には元要求と対象ソースの根拠を持たせる。原文の結論や重大度を変更する必要がある場合は、新しい訂正依頼と後続レビューを残す。

修正が必要なら採番済み`implementation_plan_NNN_MMDD.md`へ、対象指摘、理解、対応・反証方針、変更対象、影響、完了条件、検証方法をまとめる。承認はその計画の内容識別と対象集合に結び付ける。AIが内部に承認フラグを書くことだけで、人の実装承認があったとは扱わない。

修正提出は変更対象、コミットまたは内容識別、実施した確認、未実施事項を記録し、計画対象だけでなく全製品対象の内容識別も固定する。再QA時にその全製品snapshotが変わっていれば新しい状態へ自動採用せず停止する。修正済みの自己申告と独立検証済みを別状態にする。指摘の誤りをローカルが発見した場合も、自分で指摘を消さず、根拠付きの再確認依頼を作る。

### 7. 状態はローカルで管理し、過去結果を保持する

ローカル状態契約を`unified-qa-workflow-v1`とする。実行は選んだ依頼IDに対して行い、複数の進行中依頼がある場合は自動的に無関係な案件を選ばない。

状態にはリポジトリ、宛先、サイクル、初回・今回基準、固定要件と識別値、下書き／正式依頼の区別、製品・運用パス集合、依頼・レビュー・計画の相対パスと内容識別、訂正ID・提出版・置換関係・有効版・予約保存先、取得元、未解決指摘、修正提出、実装承認、公開到達点、終了判断、次操作を保持する。履歴は採番済みのサイクル状態を保持し、同じサイクルの操作履歴はrevisionとイベントで追跡する。

| 状況 | 次の担当・操作 |
| --- | --- |
| 目的・対象・基準が不足 | ユーザーが不足情報を確認する |
| 対象確定待ちの下書き | ユーザーが表示対象のローカルcommitまたはクラウド公開を指示する |
| 依頼準備済み・未公開 | ユーザーがクラウド公開を指示する、またはローカル担当へ渡す |
| 公開・手渡し待ち | ユーザーが表示された依頼をクラウドへ渡す |
| レビュー待ち | クラウド／ローカル別担当が結果を書く |
| 結果不整合 | ユーザーが訂正依頼文を担当へ渡す |
| 修正計画あり・未承認 | ユーザーが計画を確認して修正を指示する |
| 承認済み修正 | ローカル実装担当が許可範囲を修正・確認する |
| 修正提出済み | 独立担当へ再QA依頼を渡す |
| 必須確認不足 | 確認担当へ追加検証を依頼する、または残余事項をユーザーが判断する |
| 技術的な終了候補 | ユーザーが残余事項を確認して終了判断する |
| 終了判断済み | 別途指示された統合操作へ進む |

状態ファイルの更新は入力revisionを照合し、排他と原子的な書込みを行う。同じ依頼・内容の取込は再利用し、再試行の途中成果を識別する。状態確認だけでファイルを生成・更新しない。担当識別の申告だけで独立性を完全に証明できるとは主張せず、同一実装チャットの禁止と担当・実行経路の記録を併用する。

### 8. 公開は製品対象版と依頼のcommitを分ける

公開前に、現在のbranch、remote、承認済み対象パス、Git差分とindex、送出するcommit一覧を表示・照合する。公開はmain/master以外の選択済み開発ブランチに限り、force-pushや暗黙の履歴統合をしない。

対象製品のcommitを先に固定して`reviewed`にし、その後、そのSHAを参照する依頼を別commitへ保存する。対象が既にcommit済みならその版を再利用し、空commitや事前checkpointを作らない。依頼commitの分離に加え、第3節の集合選別で過去サイクルの依頼・結果も製品差分から除く。状態管理ファイルや取込原文を無条件で公開集合に含めない。

既存の無関係な変更とステージ済み内容を保持する。承認済み対象を分離できる作業領域ではその集合だけを扱い、分離を検証できない場合は具体的な対象と必要操作を示して停止する。全ファイルstage、stash、reset、cleanを自動で行わない。本Changeの開発自体は隔離作業ツリーを使う。

remoteへ送る履歴はcommitのパス集合だけでなく祖先も確認する。既存の未公開コミットが承認範囲外なら公開指示を流用せず、実際の送出範囲の確認へ戻す。remote分岐があれば停止し、別途安全な統合判断へ戻す。

クラウドが同じ開発ブランチへ結果を保存してremoteだけが先行した場合は、結果取得とブランチ更新を分離する。結果取得はMarkdownの読取りだけで完了する。次の明示的な公開操作では、remote先行差分が当該依頼で許可したレビューArtifactだけで、ローカルHEADがその祖先であり、分離した作業領域で既存差分を保持できると確認した場合に限り、成果物だけのfast-forwardを行ってから修正対象をcommitする。製品差分の混在、許可外Artifact、独自commitとの分岐では停止する。これにより通常の結果返却で毎回不要な競合を作らず、PRの製品変更を自動mergeすることもない。

push後は取得したremote tipに対して対象commitと依頼commitの到達可能性を確認する。途中失敗の再試行は既存commitを再利用し、公開成功とQA完了を混同しない。GitHubへ依頼を保存してもクラウドAIへの手渡しはユーザーが行う。

### 9. 保存場所と互換・配布を明示する

運用ファイルは各リポジトリの`docs/Artifacts/`以下へ保存する。採番規則を使ってローカルで依頼・レビュー・訂正依頼・訂正版レビューの相対パスを予約し、依頼とJSONから明示参照する。生成時点のJSTで命名し、メタデータのcreatedは保持する。クラウドには確定した保存先とメタデータ形式を渡す。

旧blindの4結果ファイルは元依頼と組で読み、Gate、指摘とタスク、対象版の一致を確認する。新しく必要な目的・基準が旧記録にない場合は確認待ちにする。旧原文の書換えと旧caseへの反映は行わない。

同期スクリプトはパッケージ別にruntimeと必須ファイルを検査できるようにする。VERSIONだけでなく相対パス・サイズ・SHA-256の差異を表示し、配布先の未知の差異を未承認で上書きしない。既存2スキルのruntime同一性は維持する。配布先の`prepare-case`と`next_step`追加は別の差異として保持し、新スキル追加のついでに戻さない。

## 制約と対策

- クラウドが書式を守らない → 不足箇所だけを示す訂正依頼を生成する。原文を勝手に補完しない。
- Markdownの構造が合っていてもレビュー内容が誤る → 元要求・対象版の根拠をAIが確認し、異論は根拠付き再QAへ渡す。
- クラウドが実行環境を持たない → 実施・未実施を分離し、必要な検証をローカルの確認担当へ案内する。
- GitHub上で返却形態が異なる → 同branch・別branch・PR・本文を同じ依頼照合に通し、取得元を記録する。
- ユーザーが次操作で迷う → 成功時だけでなく待機・拒否にも担当・操作・理由・依頼文を返す。
- 小さなQAにも重い運用を持ち込む → 正式case登録を省き、クラウド成果物はMarkdown 1つにする。検査を対象固定・承認・結果対応・必要な証拠へ限定する。
- 配布先が開発元より先行する → 同じVERSIONの差異も検出し、実同期を別工程にする。

## 開発・検証・配置の順序

4書類のレビューと実装承認後、調査HEADを基点に`codex/qa-skill-integration`と隔離作業ツリーを準備する。レビュー済み文書は内容を照合して引き継ぎ、既存削除と未追跡マニュアルを持ち込まない。

新CLI・テンプレート・状態・回収・再QAをfixtureと一時Gitリポジトリで検証し、代表会話と旧機能の回帰を確認する。実クラウドQAの指示がない段階では、fixture成功と実環境の未確認を分けて報告する。独立QAの担当は実装担当と分離する。

終了判断後の統合先は既存masterである。統合、masterのpush、外部配置は対応する明示指示の範囲で実施する。旧スキル削除はこのChangeでは行わない。新機能を取り消す場合は追加した対象と当該ラウンドの差分だけを戻し、既存case・旧runtime・配布先に復元操作をしない。

## 実装時に取得する環境情報

CLIへの具体的な引数割当て、取得するGitHub認証状態、クラウドの書込み可能な返却形態は実装・実行時の環境確認事項である。取得不能時の挙動は仕様で確定しており、取得できた環境に応じて変わるのは案内する経路である。仕様と作業範囲を変更する未決定事項は残していない。
