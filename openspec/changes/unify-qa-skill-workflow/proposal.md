# QA依頼とローカル修正を一つの入口で繰り返す提案

update: 2026-10-04 18:54 (JST)
author: Codex (GPT-6)

## 変更が必要な理由

`quality-review`と`quality-response`は管理用語と次工程の入力が複雑で、利用者が次に何を渡せばよいか判断しにくい。`blind-qa-cycle`のクラウド依頼・結果回収・修正・再QAを、Python実行環境が不明なクラウドにも渡せる依頼と、平易なローカル操作でつなぐ必要がある。

## 変更内容

- 新しい`quality-qa`スキルを普段の入口にし、「QA依頼」「結果確認」「承認後の修正」「再QA」「状況確認」を案内する。各操作で次担当・操作・理由・依頼文を返す。
- QAの前段でGit状態を読み取り、実装開始のclean baselineを安全に作るための案内を行う。既存変更は自動整理せず、対象・無関係・不明を分類して人の選択を待つ。
- クラウドAIはGitHubの固定対象をレビューし、指定DIRへ日本語Markdown 1ファイルを書く。QA管理runtimeの導入は要求しない。依頼に製品の実行検証契約がある場合は、利用可能なPython等で指定検証を実行し、Evidenceを残す。
- inviteは固定対象commitに含まれるQA Skillと出力契約のSHA-256を固定し、Cloud Reviewerにその版を読んでから監査するよう指示する。取得不能または不一致はHOLDとして記録する。
- 受入基準は依頼とレビュー双方へ安定ID付きで全件列挙し、原文・件数・順序・fingerprintの一致を取込時に検査する。
- ローカルが結果を取り込み、指摘・根拠・修正案を整理して修正計画を準備する。修正は計画承認後にローカルで行う。
- 明示的な「クラウドQAに出して」で、公開対象を表示して対象限定commit・開発ブランチへのpush・到達可能性検査まで行う。単なる依頼文作成では公開しない。
- 指定ブランチ、別ブランチ、PR、本文返却からレビューだけを回収し、対象版・基準・サイクル・指摘対応を検査する。
- 再QAは初回の目的・基準、前回指摘、修正差分、影響箇所を引き継ぎ、過去の結果を保持する。
- 修正提出時に全製品対象のsnapshotを固定し、提出後に別製品ファイルが変わっていれば再QAへ自動採用せず停止する。
- 重大問題と要求未達の解消後、残余事項を示してユーザーの終了判断へ進む。QA結果から自動受入・既定ブランチ統合は行わない。
- 未commitの対象はSHA固定前の下書きに留め、明示されたローカルcommitまたはクラウド公開で対象を確定する。依頼準備だけではcommitしない。
- 製品差分と登録済みのQA運用成果物を個別パスで区別し、再QAに過去の依頼・結果が混入しないようにする。
- 訂正レビューは同じ依頼・対象・サイクルの新しい提出版と予約保存先で受け取り、原文を保持して有効版を選ぶ。
- ローカルQAも同じ依頼・結果契約で扱う。リポジトリ名・ブランチ・承認規則を取得して他リポジトリでも利用する。
- 旧Quality-*と旧blindの4成果物を互換対象として保持する。追跡可能な`quality-qa`と`blind-qa-cycle`パッケージを作り、Cloud cloneでQA記録・詳細Finding・実施側taskを生成できるようにする。旧正式案件の契約変更、外部配置、旧版削除、自動AI起動・送信は含めない。

## 対象となる機能

### 追加する機能

- `unified-qa-workflow`: 平易な操作、対象固定、クラウドMarkdown契約、公開、ローカル回収、修正計画と承認、再QA、終了案内、旧結果読込、汎用配置を一貫して提供する。

### 変更する既存機能

なし。既存の`spec-driven-qa`、`proportional-qa-gates`、`reviewer-verification-integrity`は旧運用の契約を維持する。新機能は旧case APIを必須とせず、既存の正式case正本を書き換えない。

## 影響範囲

- `quality-loop/qa_workflow/`: 新しいローカル管理処理の開発正本。Python 3.10以上の標準ライブラリを使用する。
- `quality-loop/skills/quality-qa/`、`quality-loop/skills/blind-qa-cycle/`: Cloud cloneから読める追跡可能な自己完結パッケージ。前者はローカル状態と単一Markdown結果を扱い、後者はCloud監査の4成果物と詳細task契約を扱う。
- `quality-loop/tests/`と関連構造定義: 新機能の正常系・拒否系・Git操作・旧形式読込・パッケージ検証。
- 現行README、機能仕様、配布説明、`scripts/sync_productivity_skills.py`: 利用入口と差異検査の更新。実同期は含めない。
- `docs/Artifacts/`: 日本語・JST・採番済みの依頼、レビュー、修正計画、ローカル状態、検証記録。
- GitHubへのアクセスにはローカルの`gh`とGitを利用する。公開・クラウドAIへの手渡し・結果保存・取込は別の到達状態として記録する。

旧runtime、他リポジトリ、グローバル配置、既存case、アーカイブの改変は対象外。開発は承認後に`codex/qa-skill-integration`で行い、終了後の統合先は既存`master`とする。
