# QA機能完全互換性とLegacy互換性の設計

## 設計コンテキスト（Context）

目的と変更理由は`proposal.md`を参照する。本設計では、既存のReviewer／Author契約、QA-0006／QA-0007で確認されたdigest分離、アーカイブ済み旧版、現在のステージング版を同一リポジトリ内で比較する。Gitリビジョンを固定できない環境があるため、ファイル内容のSHA-256、Manifest、Bundle識別子、Agent／Run識別子を組み合わせてEvidenceを固定する。

比較は実際のSkill配備先を変更せず、次の3つの読み取り専用入力Bundleを明確なルートで扱う。

1. `legacy`: アーカイブ済みReviewer／Authorの旧版。
2. `candidate`: Contract v1.2候補版。
3. `compact`: 共有コアと2つの薄い入口によるコンパクト版。

各Bundleは独自のManifestとdigestを持ち、実行時のカレントディレクトリやPython import経路によって別Bundleのコードを参照しない。

機能台帳は43件の統合集合として維持する。Legacy ZIPに実在する24件はLegacy互換対象、Legacyに存在しない19件はContract v1.2以降の新規機能として分類し、後者をLegacy互換欠落とは判定しない。新規機能もCandidate／compact間および仕様正本に対しては完全に検証対象とする。

## 目標と非目標（Goals / Non-Goals）

**目標:**

- Legacyの公開・実行可能機能を43機能IDの台帳へ固定し、台帳外の入口を検出する。
- Reviewer／Authorの各機能について、三版の引数、終了コード、JSON必須項目、状態、副作用を同一fixtureで比較する。
- 差分を欠落、意図的非互換、診断・表示差分へ分類し、未説明の差分を受入候補にしない。
- Candidateとcompactが、自己クローズ、未知Finding、stale digest、Evidence、Workspace境界など既存の安全契約を維持することを確認する。
- 外部AIのAgent／Runごとの結果を混在させず、Observedと`unverified`／`evidence-gap`を分離する。

**非目標:**

- 外部Skillディレクトリへの配置、旧版の削除、commit、pushを行わない。
- 旧履歴やQA正本を自動変換・書換えしない。
- Legacyの安全でない挙動を互換性の理由にCandidateやcompactへ戻さない。
- Token数、Latency、正答率を、実測経路がない状態で推定して完了判定しない。

## 技術的判断（Decisions）

### 1. 三版を同じハーネスから起動する

比較ハーネスは、版を引数で明示し、版ごとのBundleルートからLauncherまたはCLIを起動する。実行前にManifest、digest、許可された入口を検証し、標準出力・標準エラー・終了コード・副作用のスナップショットを版別Runディレクトリへ保存する。

別々の手動コマンドを採用すると、Promptや環境条件の差を検出しにくく、結果の取り違えが起こるため採用しない。単一Bundleだけをテストする方式も、Legacy互換とコンパクト化による差分を同時に証明できないため採用しない。

### 2. 機能台帳とfixtureを分離する

機能台帳は「何を比較するか」を定義し、fixtureは「どう観測するか」を定義する。台帳の各行に機能ID、役割、入口、引数、期待終了コード、JSON必須項目、状態、副作用、比較クラスを記録し、fixtureの結果から台帳の対応Evidenceへリンクする。

台帳だけで互換とみなす方式は実行不能・副作用欠落を見逃すため採用しない。逆に全130ファイルを個別に比較する方式は内部実装差分を過度に扱い、公開契約の判定を不明瞭にするため採用しない。

### 3. 判定を層別化する

各実行結果を次の順序で評価する。

1. **同一性:** Bundle、版、Manifest、digest、Agent、Runが確定しているか。
2. **実行:** 入口が起動し、期待する終了コードと出力形式を返すか。
3. **契約:** JSON必須項目、状態遷移、権限、Evidence境界が正しいか。
4. **互換性:** Legacyとの差分が分類済みで、正本仕様と移行理由があるか。
5. **集計:** 未検証を合格へ昇格せず、機能ID単位と全体の結果を分けて報告する。

各版の機能または契約が比較対象として存在しない場合は、`not-applicable`または`intentional-noncompatibility`として理由・仕様・Evidenceを記録する。存在するが実行結果や契約突合が不足する場合は`evidence-gap`とする。いずれもLegacy完全互換の合格数には含めない。

診断文の完全一致を要求すると安全契約に影響しない文言差を誤って非互換とするため、診断コード・終了コード・構造化フィールドを優先し、自由文は別分類とする。

### 4. EvidenceをAgent／Run単位で隔離する

外部AIを使う場合は、`agents/<agent_id>/<run_id>/`をEvidenceの書込み単位とし、各Runに入力Prompt、出力、時刻、モデル条件、実行件数、未実行件数、Token／Latencyの取得状態、Bundle digestを保存する。Coordinatorの集計は各Runのmanifestとresultsだけを読み、共有の正本レビュー記録を直接変更しない。

複数AIの結果を単一ログへ追記する方式は、モデル条件と出力の帰属を失うため採用しない。外部AIがTokenまたはLatencyを提供しない場合は、数値を補完せず`unverified`とする。

### 5. 受入ゲートを段階化する

次の順序でゲートを設ける。

- **G0:** Legacy／Candidate／compactのルート、Manifest、digest、キャッシュ除外を確認する。
- **G1:** 43機能ID台帳と台帳外入口の差分を確定し、Legacy互換24件と新規機能19件を分類する。
- **G2:** golden／negative／cross-skill／Legacy互換fixtureを三版で実行する。
- **G3:** 互換差分、安全境界、状態、副作用、Evidenceを独立QAへ提出する。
- **G4:** 人間裁定で、未解決Finding、`unverified`、意図的非互換、残余リスクを承認または保留する。

G0からG2の自動テスト合格だけでは本番配備を許可しない。G3とG4の完了、および別Changeの配備承認を必要条件とする。

## リスクとトレードオフ（Risks / Trade-offs）

- **[Legacyの正本がアーカイブである]** → Bundle digestと保存場所を固定し、アーカイブ内容を変更せず、変更時は新しい基準Runとして扱う。
- **[43機能IDの抽出漏れ]** → 台帳と公開入口の双方向照合を行い、未登録入口を非合格候補として報告する。Legacyにない19件は新規機能として別分類する。
- **[三版の実行環境が混ざる]** → 版ごとにルート、環境、Runディレクトリを分離し、Launcherの解決先とManifestをEvidenceへ保存する。
- **[Legacyとの差分を過度に互換要求する]** → 安全契約を優先し、意図的非互換と診断・表示差分を独立分類する。
- **[LLM動的Evidenceがモデル依存になる]** → Agent、モデル、設定、Prompt suite、実行日時を必須記録し、単一モデルの結果を一般化しない。
- **[Token／Latencyが未計測のまま残る]** → `unverified`を維持し、正答率やサイズの結果と混同しない。必要なら後続の測定Changeへ分離する。
- **[版ごとの契約有無を同じ合格条件で扱う]** → 版別の適用可能性を記録し、存在する契約の安全性と、存在しない契約の非互換性を別々に判定する。
- **[サイズ目標が安全機能を圧迫する]** → 1,760行以下は参考目標とし、テスト、仕様、安全境界、最小完全fixtureを削除して達成しない。

## 移行とロールバック（Migration Plan）

1. Legacy Bundleを読み取り専用の基準として複製し、Manifestとdigestを保存する。
2. Candidateとcompactを別ルートへ配置し、混入検査とサイズ計測を行う。
3. 機能台帳とfixtureを確定し、三版比較の結果をAgent／Run単位で保存する。
4. 差分分類、独立QA、人間裁定を完了し、未検証項目と残余リスクを明示する。
5. 不合格または判定不能の場合は、外部配備を開始せず、比較結果とEvidenceを保持したままcompactの利用を停止する。
6. 本番配備は別Changeでバックアップ、dry-run、配置検証、ロールバックを実施し、明示承認後にのみ行う。

ロールバックは外部配備前であれば実行不要であり、Candidate／compactの参照を止めてLegacy基準Bundleへ戻す。外部配備そのものは本Changeで実施しないため、配備後の復元手順は後続Changeの責任範囲とする。
