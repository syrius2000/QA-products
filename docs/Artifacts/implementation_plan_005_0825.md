## 4. 圧縮方針

### 4.1 守る不変条件

- ReviewerとAuthorの役割分離、自己検証・自己クローズ禁止
- `fixed-and-verified`と`risk-accepted`の区別
- `handoff.md`の信頼境界、origin、freshness、semantic/content digestの検証
- Contract v1.2の状態遷移、Finding分類、REQUIREDマーカー、証拠階層
- 秘密情報を記録へコピーしないこと
- Python実行時の標準ライブラリのみという依存関係境界
- 既存のCLI入口、終了コード、JSON出力、テンプレートの必須フィールド

### 4.2 採用方針

- **共有コア＋2つの薄いSkill入口を第一候補とする。** Skill名自体がReviewerまたはAuthorという役割をLLMへ伝えるため、単一Skillへ強制統合しない。Author入口は共有コアを利用するが、Reviewer用の独立レビュー・検証・クローズを指示しない。
- 共通処理を共有コアへ抽出し、ReviewとAuthorは役割別の薄い入口にする。共有コアにも役割引数・権限チェックを置き、入口文書だけに安全境界を依存させない。
- 小さなスクリプトを機械的に一つへ連結せず、責務境界を保った共有モジュールとCLIへ統合する。Authorの提出保存・実行ポリシーとReviewerの独立レビュー・検証は別入口として識別可能にする。
- スキーマは正本を一元化するが、JSON SchemaをPython型へ置換するかは互換性検証後に決定する。
- referencesは、常駐指示（`SKILL.md`）と詳細仕様（`SPEC.md`）に分け、必須規則・分類・証拠・状態遷移を一度だけ記載する。
- examplesは、single-cycleとmulti-cycleの最小完全例を維持し、意味のない重複例だけを削減する。
- MANIFEST、README、INSTALL、evals、既存リンクを移行後の構成に合わせる。

### 4.3 圧縮量の見通し

1/3以下は、テストや必須の完全サンプルを削ることではなく、次の2つの集約効果を主な根拠として検証する。

- スクリプト集約: 28本の個別スクリプトに分散した引数解析、共通検証、import、JSON入出力を共有コアへ集約し、実装部分を概ね2,000行から500〜600行規模へ圧縮する。ただし、Phase 0の機能台帳で実際の重複量を確認する。
- 文書蒸留: 分類学・証拠基準・状態遷移・安全規則を`SPEC.md`へ集約し、各`SKILL.md`を役割別の行動規則に限定する。目安として分散文書約600行を約200行規模へ整理する。

この見通しは目標であり、挙動差分・負のテスト・役割分離を満たせない場合は、行数目標より能力維持を優先する。

## 5. 実施フェーズ

### Phase 0: ベースラインと互換性台帳の固定（承認後の開始点）

1. 現行130ファイルの機能ID、引数、終了コード、出力形式、依存関係をマトリクス化する。
2. 全スクリプト、テスト、スキーマ、テンプレート、サンプル、evalをReview固有、Author固有、共通の3分類へ割り当てる。
3. ファイル数・行数・バイト数・ハッシュ・公開入口を再集計し、集計条件と基準版を固定する。
4. 現行テストと代表的なCLI実行をベースラインfixtureとして保存する。正常系だけでなく、拒否系・境界系・秘密情報検出・権限逸脱を含める。
5. 以後の圧縮版は、この台帳とfixtureを変更理由なしに削除・簡略化しない。

### Phase 1: 統合設計と小さな試作

1. 第一候補を「共有コア＋2つの薄いSkill入口」とし、単一統合Skillは比較記録を残したうえで原則採用しない。
2. Author側の提出権限とReviewer側の検証権限を同一モジュールへ不用意に混ぜない設計を確定する。自己レビュー、自己検証、自己クローズへ到達できないことを設計上確認する。
3. まず変更対象を別ステージ領域または一時作業ディレクトリに作り、現行配布物を直接上書きしない。
4. 既存入口から新実装を呼べる互換層を設け、差分検証が終わるまで旧実装を保持する。

### Phase 2: 共通コアと役割別入口の実装

1. digest、JSON入出力、契約・スキーマ検証、状態遷移、イベント、リンク、秘密情報、cycle制限を共通化する。
2. Review固有の独立レビュー・ケース作成・handoff・closeと、Author固有のresponse保存・execution policyを薄い入口へ残す。
3. CLI統合を採用する場合も、サブコマンドごとの公開契約、終了コード、エラー分類を維持する。
4. 実行時依存を増やさず、既存のPython対応範囲を維持する。

### Phase 3: 文書・スキーマ・例の蒸留

1. `SKILL.md`はエージェントが常時読む規則に限定する。
2. 詳細な正本仕様を`references/SPEC.md`へ統合し、重複定義を削除する。
3. スキーマを削除・統合する場合は、旧スキーマで受理または拒否された全ケースを差分テストする。
4. テンプレートと例は必須フィールド、禁止事項、状態遷移が確認できる最小完全セットを残す。

### Phase 4: 差分QA、移行、配布判定

1. 現行版と圧縮版を同じ入力 fixture に対して実行し、出力・終了コード・拒否理由・副作用を比較する。
2. 正常系、必須欠落、古いdigest、競合revision、秘密情報、権限逸脱、自己クローズ、cycle上限、外部依存欠落を検証する。
3. 既存SkillのMANIFESTと新MANIFESTを検証し、旧ファイルへのリンク・import・CLI呼出しを検索する。
4. `pytest`、`py_compile`、`git diff --check`相当の静的検査、evalを実行する。実行不能な環境証拠は`unverified`として記録する。
5. 旧版を即時削除せず、互換確認とロールバック手順を確認してから置換対象を確定する。

## 6. 目標値と合格基準

### 目標値

- 合計行数: 現状5,287行に対して、第一目標1,760行以下（約3分の1以下）
- ファイル数: 130から20〜30程度を目安とする。ただしテスト・正本仕様・最小完全例を削って達成しない。
- `SKILL.md`: ReviewerとAuthorを別名のまま維持し、各役割の次アクション・禁止事項・返却先が明確な短い入口にする。
- 共有コアの機能は、Reviewer入口からAuthor専用の提出処理へ、Author入口からReviewer専用の独立検証へ、役割指定なしには到達できない構造にする。

### 合格基準

- 互換性台帳の全機能IDに、新しい実装または明示的な非互換理由がある。
- 現行の全テストが通過し、追加した差分・負のテストも通過する。
- 旧版と圧縮版の正常系出力、終了コード、拒否条件、副作用が契約上同等である。
- Contract v1.2の不変条件に対する独立レビューでCritical/Highの未解決Findingがない。
- ReviewerとAuthorの役割逸脱（自己レビュー、自己検証、自己クローズ）を、静的確認と負の実行テストの双方で再現不能にする。
- MANIFEST、相対リンク、インポート、インストール手順、evalが新構成に整合する。
- 実行環境で確認できない項目を完了扱いせず、残余リスクと再検証条件を明記する。

## 7. リスクと対策

| リスク | 対策 |
|---|---|
| 単一CLI化による責務混在・障害波及 | 共通コアと役割別入口を分離し、権限境界を差分テストする |
| 文書削減でエージェントの判断規則が欠落 | 不変条件台帳とevalを先に固定し、削除は重複箇所に限定する |
| JSON Schemaや終了コードの互換性破壊 | 旧版とのfixture差分テストを合格条件にする |
| 例の削減で使い方が不明確になる | 正常系・拒否系・複数cycleを含む最小完全例を残す |
| 外部Skillパスへの直接変更とロールバック不能 | 承認後もステージ作業、マニフェスト、バックアップ、置換前後検証を必須にする |
