# AIエージェントと人間の協働事例：QA修正と記録整理

created: 2026-10-11 20:33 (JST)
update: 2026-10-17 15:57 (JST)
author: Codex (GPT-6)

## この事例について

この文書は、QA関連の修正・検証・文書整理を人間とAIエージェントが対話しながら進めた事例を、部内共有向けに要約したものである。会話の逐語録ではなく、判断の経緯、作業上の確認、得られた結果に焦点を当てる。

## 背景と課題

独立QA Cycle 1で、blind-qa-cycleのBaseline選択説明に不整合が指摘された。独立QAの再実行では修正後の対象が合格したが、その後のQAサイクルでは別のBaseline説明の不整合がFAILとして記録されていた。実装側は説明を修正した一方、利用者は独立再QAを行わない判断をしたため、「実装修正済み」と「QAで確認済み」を分けて扱う必要があった。

同時に、`docs/Artifacts/`には完了した計画書が残っており、どれをアーカイブできるか、現行案内や過去記録をどう整合させるかが課題になった。

## 対話を通じた進め方

1. **対象ファイルと実際の状態を確認**
   計画書038・039・041を開き、実装・利用者判断・未完了事項を読み合わせた。Plan 041はBaseline選択ルールを3文書間で揃える内容と確認した。

2. **実装修正とQA判定を分けて説明**
   3文書の説明を修正し、対象spec、相対リンク、差分を検証した。修正済みであっても独立再QAを省略した以上、Cycle 1の元判定をPASSへ変えられないことを確認した。利用者の判断に沿って、元のFAIL記録を保持したまま関連計画をアーカイブした。

3. **アーカイブに必要な関連記録も整合**
   README、Archive案内、過去のOpenSpec実装記録に残っていた古い進行状態を更新し、元の計画と保存先の対応をサマリーに記録した。Cycle 1の独立Reviewer原本は編集しなかった。

4. **strict検証の警告を具体化して修正**
   全spec strict検証が失敗した理由を対象specまでたどった。3要件にRFC 2119形式の`MUST`がなく、validatorが書式警告を出していることを説明した。利用者の指示に従って3要件を修正し、再検証した。

5. **コミット・統合・公開まで状態を確認**
   未コミットの変更を確認してコミットし、masterへfast-forward統合してorigin/masterへpushした。最後にHEAD、master、origin/masterの一致と作業ツリーのcleanを確認した。

## 結果

- Cycle 1関連の計画書038・039・041とQA記録をArchiveに整理し、案内と記録を更新した。
- Baseline修正は実装側で完了したが、独立再QAは行っていない。Cycle 1はGate `FAIL`、Finding `QA-FLOW-M01`は`OPEN`、AC-009は`UNVERIFIED`のまま保存した。
- `reviewer-verification-integrity` specの3要件に`MUST`を追記し、strict警告を解消した。
- 全specのstrict検証は9件成功、失敗0件。長文要件に関する情報レベルの案内は残る。
- 変更はmasterに統合され、remoteにもpushされた。

## この事例で示した協働上の工夫

- AIは要約や過去記憶だけで断定せず、実ファイル、Git状態、validator出力を照合した。
- 利用者の目的に応じて、計画承認、実装、検証、アーカイブ、コミット、統合、pushを区別して進めた。
- FAILの意味を「修正後の現在版も不合格」と誤読せず、固定された過去のQA判定と後続の実装修正を分けた。
- 検証の成功を過大主張せず、独立再QAをしていないことと、strict検証で残る情報レベルの案内を併記した。
- 利用者が簡単な文言修正には計画不要と指定した際は、その範囲に従って進め、検証結果を示した。

## 共有時の留意点

本事例の要点は、AIがすべてを独断で済ませたことではない。人間が目的や受入範囲を決め、AIが具体的な文書・差分・検証結果を提示し、双方で判断の境界を確かめながら作業を完了したことにある。QAのPASS、実装側の修正、利用者の受入判断はそれぞれ異なる状態として記録している。
