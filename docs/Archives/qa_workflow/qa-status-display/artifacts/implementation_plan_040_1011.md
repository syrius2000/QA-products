## 言語選択と互換性

1. スキルへの言語指定は`lang=ja`または`lang=en`とし、単独の`en`指定も英語表示選択として受け付ける。指定なしは`ja`。`blind-qa-cycle`の`review`や`cloud`などの操作モードとは独立した表示設定として扱う。
2. 内部CLIには`--lang {ja,en}`を追加する。言語指定なしは日本語の利用者向け表示を選ぶ。引数の位置と実例を各CLIのヘルプとスキル案内で一致させる。
3. `quality-qa`の通常テキスト出力は日本語表示を既定とする。`--lang en`では現行の状態コードを用いた表記を保持する。ただし、根拠を超える「安全」等の説明の補正は両言語に適用する。これは現行の混在表記も含む互換表示であり、全メッセージの英訳とは別の要件として扱う。
4. 正式案件CLIの既定JSON出力は維持する。`status --format text`を追加し、スキルが人へ案内する際はこの表示を利用できるようにする。JSONを受け取った場合も、スキルの応答は選択言語で状態を説明する。
5. JSONのキー、状態コード、Role、操作名、判定値、ID、コマンド、パスは既存の契約を維持する。人向けラベルを機械値に書き戻さない。
6. 言語設定は表示単位で渡し、既存案件やQA依頼の保存状態を移行・書換しない。不明な値は原コードを明示して「未定義の状態」と表示し、成功や終了を推定しない。不正な言語指定は入力エラーにする。
7. Artifactの本文・見出しを日本語にするリポジトリ規則は維持する。英語表示選択は利用者向け状態説明に適用し、既存Artifact、固定された受入基準原文、機械契約の文字列を翻訳・上書きしない。

## 利用者向け状態を5工程にまとめる合意

2026-10-11、利用者が「5工程にまとめる」を選択したため、基本表示を次の5工程にまとめる方針を確定した。表示数を減らすために内部の状態遷移や承認工程を削除しない。この設計方針への合意は、コード実装を開始する承認とは区別する。

| 基本表示 | 利用者が把握すること | 主な対象 |
| --- | --- | --- |
| 準備 | 対象版やQA依頼を整えている | 下書き、対象確定、依頼準備 |
| QA・確認 | レビューまたは検証を待つ・実施している | レビュー依頼、結果確認、計画レビュー、修正結果の独立検証 |
| 修正 | 指摘への計画や対応を作っている | 修正計画作成、承認済み修正、応答準備 |
| 判断待ち | 利用者または統括者の判断が必要 | 計画承認、残余リスクの判断、受入裁定 |
| 終了 | 終了判断が記録されている | 受入、リスク付き受入、却下、通常QAの終了判断 |

基本表示に「詳細」「次の担当」「次の操作」を添える。止まっている場合だけ「停止理由」と「再開条件」を明示し、必要入力や未解決数は該当時に添える。内部コードは詳細表示または機械JSONに残す。終了の内訳も詳細へ残し、却下やリスク付き受入を成功と誤認させない。

例として、`content_pending`は「QA・確認／レビュー内容の妥当性を確認待ち」、`planned`は「判断待ち／修正計画の承認待ち」と表示する。単に「確認中」とだけ示さず、何が必要かを次操作で具体化する。

QA判定の`PASS`、`HOLD`、`FAIL`、`INCONCLUSIVE`は、進行工程と別の項目として「基準を満たす／保留／基準未達／判定不能」と説明する。判定を工程の種類に追加して基本表示数を増やさない。言語指定の`en`は現行コードによる表示を選ぶ。

工程への対応付けは状態コードだけでなく、次担当、承認の必要性、レビューの未達・未検証、停止理由も参照して決める。例えば`reviewed`は、未達があれば修正、確認不足ならQA・確認、受入裁定が必要なら判断待ちとなる。未知状態は5工程へ推測で押し込まず、未定義として確認を求める。

内部状態自体の削減は、既存データの移行と承認・Role制約の再設計を伴う別の変更になるため、本計画では利用者向け表示の整理を行う。

## 現行の種類数と変更後の種類数

ここでの水準は順序尺度ではなく、工程または評価のカテゴリ数を意味する。

| 対象 | 現行の進行状態 | 変更後の利用者向け基本表示 |
| --- | --- | --- |
| `quality-qa` | 11種類 | 5工程 |

通常QAの11種類は`draft`、`prepared`、`published`、`waiting`、`invalid`、`content_pending`、`reviewed`、`planned`、`approved`、`submitted`、`decision`である。

正式案件の11種類は`reviewer-action`、`implementer-plan`、`reviewer-plan-review`、`implementer-action`、`reviewer-verification`、`reviewer-final-assessment`、`owner-adjudication`、`held`、`accepted`、`accepted-with-risk`、`rejected`である。`rework-requested`は統括者の裁定値であり、その後の案件状態は計画または修正の工程に遷移するため、独立した進行状態には数えない。

内部の11種類は維持し、利用者向けの基本表示を5工程に集約する。指摘単位の状態や修正ループの段階を、この工程の数に混ぜない。

## QA評価結果の日本語表示

利用者の追加指示により、状態に加えてQA評価結果も日本語表記にする。総合QA判定の種類数は4種類を維持する。

| 現行コード | 既定の日本語表示 | 意味 |
| --- | --- | --- |
| `PASS` | 基準充足 | 対象のQA基準を満たす |
| `FAIL` | 基準未達 | 対象のQA基準を満たさない |
| `HOLD` | 保留 | 追加確認や判断が必要で結論を保留する |
| `INCONCLUSIVE` | 判定不能 | 根拠が不足し結論を出せない |

この4種類は`quality-qa`と`blind-qa-cycle`の総合判定である。正式案件の2スキルには別体系の最終リスク評価勧告が4種類あるため、意味を保った日本語表示とし、総合QA判定へ無条件に置き換えない。

| 正式案件の評価勧告コード | 既定の日本語表示 |
| --- | --- |
| `accept` | 受入を推奨 |
| `accept-with-conditions` | 条件付き受入を推奨 |
| `require-remediation` | 修正が必要 |
| `defer` | 判断を保留 |

受入基準ごとの3種類は`PASS`＝基準充足、`FAIL`＝基準未達、`UNVERIFIED`＝未検証とする。実行チェック結果の4種類は`PASS`＝確認成功、`FAIL`＝確認失敗、`NOT_RUN`＝未実行、`ERROR`＝実行エラーとする。未検証と判定不能、未実行と実行エラーを混同しない。

`en`指定時は既存の評価コードを表示する。機械JSON、`STATUS.md`の単一トークン、固定したレビュー契約の解析用コードは維持し、利用者向けの表示で日本語に置き換える。統括者の最終裁定は評価勧告とも別の記録として扱う。

## 状態の見直し方針

現在の判定条件に基づく表示を作り、単なるコードの直訳で済ませない。全既知状態、指摘結果、担当、次操作、修正ループ段階を実装時に列挙して対応表を確定する。

以下は基本表示とは別の、詳細説明用の対応表である。

| 現行の状態またはコード | 日本語の詳細説明案 | 説明で必要な区別 |
| --- | --- | --- |
| `draft` | QA依頼の下書き・対象版の確定待ち | レビュー開始済みではない |
| `prepared` | QA依頼を準備済み | クラウド向けでは公開指示待ち、ローカル向けでは手渡し可能 |
| `published`、`waiting` | 依頼公開済み／レビュー結果待ち | 公開とレビュー完了を区別する |
| `content_pending` | 取得したレビュー内容の確認待ち | 構造確認済みでも意味の妥当性は未確認 |
| `invalid`または訂正記録あり | 結果の不備・訂正待ち | 不備の理由と訂正の担当を示す |
| `reviewed` | 内容確認済み | 未達、必須確認不足、終了判断候補を個別の条件で示す |
| `planned` | 修正計画の承認待ち | 修正の実行許可は未取得 |
| `approved` | 承認済み・修正と確認を行う段階 | 承認範囲と次操作を示す |
| `submitted` | 修正を提出済み・再QA待ち | 修正提出と独立検証の完了を区別する |
| `decision` | 利用者の終了判断を記録済み | 統合や配備が完了したとは表示しない |
| `reviewer-action` | レビュー担当の確認待ち | 次担当をレビュー担当と示す |
| `implementer-plan` | 実装担当の修正計画提出待ち | 計画の提出と修正を区別する |
| `reviewer-plan-review` | 修正計画のレビュー待ち | 実装承認条件を維持する |
| `implementer-action` | 実装担当の修正・応答提出待ち | 実装許可範囲を示す |
| `reviewer-verification` | 修正結果の独立検証待ち | 応答提出のみで完了としない |
| `reviewer-final-assessment` | 残るリスクの評価待ち | 検証と受入判断を区別する |
| `owner-adjudication` | 統括者の受入判断待ち | AIによる自動受入を行わない |
| `PASS` | 判定基準を満たす | 必須検証と利用者の終了判断は別に示す |
| `HOLD` | 保留・追加確認または判断待ち | 保留理由と解除条件を示す |
| `FAIL` | 判定基準を満たさない | 未達事項と次の対応を示す |
| `INCONCLUSIVE` | 根拠不足で結論を出せない | 不足する根拠を示す |

正式案件の保留・再レビュー・終端状態、指摘分類、重大度、検証結果は、実装時に正本の列挙値・遷移から漏れなく対応させる。`verified`、`unverified`、`not-verified`などの意味を混同しない。

### 総合状況の説明で補正する点

追加の読取り調査で、`quality_loop/markdown_report.py`の総合状況には次の過剰な推論があることを確認した。正本のQA判定・状態遷移は維持し、表示から導く説明と表示色を、根拠に合う範囲へ補正する。

| 現状の説明 | 補正の方針 |
| --- | --- |
| `accepted`を「受入完了・安全」と表示 | 「統括者が受入済み」と示す。受入判断だけで安全性全般を保証しない |
| `accepted-with-risk`を一律「条件付き受入」と表示 | 「残余リスクを受容して受入済み」と示す。追加条件の有無は記録された条件に基づく |
| 最後の分岐を一律「全件検証完了・安全」と表示 | 統括者の判断待ちと検証状態を分ける。未知状態や根拠不足から検証完了を推定しない |
| `reviewer-action`を一律「初回レビュー待ち」と表示 | 初回評価と、基準更新後の再レビューを案件の記録に基づき区別する |

受入状態、レビュー回数、未解決指摘、観測限界、次工程の組合せを代表案件で検証する。総合表示が次担当・次操作と矛盾せず、観測した検証範囲以上の安全性を主張しないことを受入条件に追加する。

修正ループは完了段階、停止段階、停止理由、次の段階、再開に必要な操作を日本語で示す。公開走査拒否等は一般の工程表示より優先して説明する。`blind-qa-cycle`は既存の記録から確認できることだけを示し、`PASS`だけを根拠にサイクル終結やOwner受入を推定しない。

## 記載を承認された必須追加要件

2026-10-11、利用者から以下の3点を計画へ記載する承認を得た。今回の承認範囲は計画への反映であり、コード実装の開始承認とは区別する。

### 1. QA基準を確認して固定する

今回の独立QA開始前に、基準にする計画書名、またはOpenSpec Change名と対象文書を利用者へ短く提示する。文書の版と受入基準のID・原文・一覧を記録し、確認された内容を監査基準として固定する。OpenSpecでは提案・仕様差分・設計・タスクの対象を示し、どの記述を評価基準とするかを明示する。文書間に矛盾があれば利用者の判断を得てから固定する。

基準の追加・削除・緩和には変更点を提示した利用者の承認を必要とする。再QAは固定した基準を引き継ぐ。基準外の指摘は区別して記録し、既存基準を無断で増減させない。この要件は今回の開発を監査するQA手順として実施する。

### 2. 内部状態から5工程への対応を確定する

全内部状態と停止条件に対して、基本表示の工程・次担当・次操作を対応表で定義する。承認待ち、公開拒否、訂正待ちなどが重なる場合の優先順位も確定する。対応表と優先順位をOpenSpecの仕様・設計へ記載し、既知状態と複合条件で表示が一意に決まることを検証する。

### 3. QA評価結果の適用対象を明示する

評価結果は評価した対象版とサイクルを明示して表示する。QA未実施の場合は結果がないことを示す。修正後の版が未評価の場合は、修正前の結果を過去結果として区別し、現在の版にも適用された評価として表示しない。総合QA判定の既存4種類は維持し、結果の有無や過去結果であることを新しい判定値として追加しない。

この3点を新規Changeの仕様と検証シナリオに対応させる。基準の確認・固定は今回のQA手順、状態対応と評価対象の明示は今回の表示機能の要件として扱う。

## 開発ブランチとOpenSpec Changeによる進め方

利用者の追加方針に基づき、新しい通常の開発ブランチを作成し、そのブランチで新規OpenSpec Changeを準備してから開発する。

- 開発ブランチ案: `codex/qa-status-ja-default`
- Change名案: `simplify-qa-status-display`
- 現行OpenSpecルート: このリポジトリ。`openspec list --json`で確認済み。
- 既存の`unify-blind-qa-cycle`、`improve-quality-qa-loop`はタスクが全件完了と表示されている。本件は既存Changeへ追記せず独立した新規Changeにする。

`openspec-ff-change`はスキル名であり、`openspec ff change`というCLIコマンドを前提にしない。スキルの手順に従い、`openspec new change`、`status`、`instructions`を使用して提案・仕様差分・設計・タスクを必要な依存順に作成する。実際の保存先はCLIが返すパスに従う。計画書・QA結果等の独自Artifactは`docs/Artifacts/`の命名規則を使用し、OpenSpecの規定ファイルはOpenSpecの保存契約に従う。本文と説明は日本語にする。

### 手順と実装前の確認

1. 方針が合意された後、既存差分を確認して新しい開発ブランチを作成する。既存ブランチが同名なら先端と内容を確認し、無断で上書きしない。作業場所は通常チェックアウトを使う。
2. `openspec-ff-change`で新規Changeを作成する。既存の本仕様と対象コードを読み、提案・仕様差分・設計・タスクを本計画と整合させる。合意済みの基本表示5工程と日本語既定・`en`選択を仕様で明確にする。
3. 仕様差分には安定した受入基準IDと観測可能なシナリオを記載する。状態対応、停止理由、終端の内訳、未知状態、英語選択、JSON互換性、読取り専用性、配布コードとの一致を監査対象として固定する。
4. `openspec validate simplify-qa-status-display --strict`で構造を確認し、仕様と本計画の差分を提示する。構造の正常性を実装完了や独立QA完了と扱わない。実装前に確定した仕様・計画への明示承認を得る。
5. 承認済みの仕様に沿って正本と4スキルを実装し、配布用の実行コードへ同じ変更を反映する。実装タスクと検証の証拠を対応させる。
6. 一時ディレクトリの代表案件・依頼を使い、日本語既定、明示`ja`、明示`en`、未知状態、不正言語、停止と再開、終了と却下、表示前後の正本不変を確認する。全既知コードの対応網羅性と現行JSON互換性を確認する。
7. 正式案件CLIのJSON経路、人向け経路、再開用Markdown、配布コードの一致、対象スキルの構造と参照リンク、関連既存テストを確認する。
8. 利用者へ計画書名またはChange名・対象文書・版・受入基準を提示して確認し、監査基準を固定する。その確定した仕様と全受入基準に対して、実装担当と別の担当・チャットで独立QAを行う。対象版と仕様の版を固定し、基準ごとに合格・不合格・未検証と証拠を記録する。独立性は担当名の申告だけでなく実行経路と記録で示す。
9. 不適合があれば承認範囲に沿って修正し、再QAへ進む。新しい範囲が必要なら計画を改定する。未検証を合格で補わず、利用者の終了判断へ渡す。
10. 最終差分、検証結果、独立QA結果、未検証事項を日本語で報告する。各編集ラウンドの前後に差分を確認し、既存の利用者変更を保持する。

### 独立QAの監査基準

独立QAは仕様差分を要求の基準とし、設計を実装方式の説明、タスクを実施状況の索引として扱う。タスクのチェックだけで仕様を満たしたと判断しない。

| 監査項目 | 必要な根拠 |
| --- | --- |
| 日本語が既定である | 4スキルの代表利用と対象CLIの実際の出力 |
| 基本表示が簡潔で意味を失わない | 5工程、全状態対応表、条件別の表示結果 |
| `en`が選択できる | 英語指定の出力と操作・判定不変の確認 |
| 停止と終了を誤認させない | 承認待ち、保留、未達、未検証、受入・却下の代表例 |
| 機械契約と保存状態が維持される | JSONの比較、状態表示前後の正本比較、関連回帰テスト |
| 正本と配布物が一致する | 対応ファイルの内容比較と配布CLIの出力 |
| QA基準が確認・固定されている | 対象文書・版・受入基準の記録、利用者の確認、再QAでの同一基準の引継ぎ |
| 5工程への対応が一意に決まる | 全状態・停止条件の対応表、優先順位、複合条件の表示結果 |
| 評価結果の対象を誤認させない | 評価対象版・サイクルの表示、QA未実施と修正後未評価の表示例 |

クラウドQAを使う場合のcommit・pushはその公開対象を示した指示を受けてから行う。ローカルの独立QAでは外部公開を前提にしない。Changeのアーカイブ、既定ブランチへの統合、外部Skill配置も別工程とする。

## 受入基準

- 言語未指定で、4スキルの状態説明が日本語となり、工程・担当・操作・理由・必要入力を理解できる。基本表示は「準備／QA・確認／修正／判断待ち／終了」の5工程にまとめ、詳細の意味を失わない。
- `en`を明示した場合は現行の表示語彙を使用でき、操作モードの選択や判定条件が変わらない。
- QA総合判定、正式案件の評価勧告、基準別判定、実行チェック結果が既定では日本語、`en`指定時は既存コードで表示され、それぞれの意味と種類数が維持される。
- 全既知状態と停止条件に説明があり、未検証、保留、失敗、修正提出、独立検証済み、利用者の終了判断を区別できる。
- 表示の変更により機械JSONの既存フィールド・列挙値、保存データ、CLIの機械利用、Role制約、承認範囲、QA判定が変わらない。
- 正本と配布用実行コードが一致し、対象に合った検証で日本語既定、英語選択、互換性、読取り専用性を確認できる。
- 新規Changeの確定した仕様・受入基準を基準とする独立QAで、全項目の結果と証拠が記録される。
- QA開始前に基準文書・版・受入基準が利用者に確認され、基準の追加・削除・緩和には変更点への承認が記録される。再QAも同じ基準を引き継ぐ。
- 全内部状態と停止条件の5工程への対応、および複合条件の優先順位が仕様で確定し、そのとおりの表示が確認できる。
- QA評価結果には評価対象版とサイクルが示され、結果なし・過去結果を現在版の判定と誤認させず、総合QA判定の4種類が維持される。
